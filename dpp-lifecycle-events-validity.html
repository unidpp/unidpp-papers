DPP lifecycle, events and validity

A post-sale event taxonomy, state machine and validity model for the Digital Product Passport: sixteen typed events, the state machine for dppStatus, the temporal profile of ISO 8601, and as-of query semantics — the operations layer that EN 18223 §4.2 mandates and the series never specifies.

01 · Scope and methodFrom a mandated log to a model

EN 18223 §4.2 mandates change logging — each change recorded with identifier, timestamp, actor and changed properties — and §4.1.2.1 gives example values for dppStatus (active, inactive, archived, invalid) without an enumeration, a state machine or transition rules. EN 18246 §4.7 requires that every creation, modification and deletion be logged non-repudiablely with an identifiable editor. EN 18221 requires historical state be preserved and archived. What no document in the series supplies is the model: what kinds of things happen to a passport after first sale, who may append them, how status changes, and what was legally true at a given time.

This contribution supplies that model. It was derived by converting the full EN and CWA corpus and the IDTA submodel set to machine-readable form, extracting every lifecycle-relevant clause, and reconciling the three incompatible lifecycle taxonomies found in the series (the identifier granularity model of EN 18219, the nine-phase model of EN 18239 Annex A, and the ISO 14040-lineage model used by the EN 18223/18220/18219 terms). The proposal is offered as workstream B input and as the normative core of a prospective lifecycle standard.

Three design rules govern everything that follows: nothing is ever edited in place — every post-first-sale change is an appended event; the event log is the authoritative record, log-anchored and distributed; and corrections never rewrite — a correction is a new event that supersedes a prior value while preserving it in the log.

02 · The event taxonomySixteen typed events

Each event type fixes what changes and which role appends it. Roles are those of EN 18239 (dealer, distributor, refurbisher, transfer of responsibility) extended with the framework's accredited-actor pattern for regulated claims.

Four cross-cutting rules bind the taxonomy. Re-evaluation: modifications and feature unlocks trigger re-running of the applicable profile's validation package, with a transitional "non-conformant pending re-evaluation" status and regulator notification per profile. Recall propagation: recalls traverse the provenance DAG downstream and notify custodians — no EN implements this; EN 18239 names take-back as a stage only — and the recall set is never enumerated centrally: the predicate is published, each custodian evaluates it locally (dark holdings under national procedure), and the initiator receives aggregates or nothing — predicate-based recall, not traversal-push enumeration. Transformation: splits, combinations and decompositions are typed events with quantity semantics — outputs carry input references with quantities and as-of state hashes, inputs transition to consumed/transformed while remaining verifiable for as-of queries, and mass balance is auditable. Carrier replacement: re-issuing a physical carrier (QR reissue) is a registry event on unchanged identity.

Installation is its own event semantics, not generic containment. An install event records child, parent, method, slot identity, pairing (none, firmware, key or module), any permanent alteration (soldered, welded, potted — possibly unrecoverable) and the performer: an installed, fastened component is a different legal object from the standalone one, with re-scoped warranty, parent-scoped slot identity and second-hand-once-removed status. Knowledge is bidirectional — the parent's manifest lists children; the child's log records its installation interval — because installation history is value-relevant provenance (a harvested battery sold standalone carries its in-vehicle history) and routes recalls, service access and end-of-life. A recoverability spectrum governs identity continuity: restorable (the child resumes standalone life), harvestable (recovered but altered — continues with harvested status and parent history), destructive (the child ceases; flows to a material passport as a transformation), absorbing (identity dissolves — recorded at finest granularity as dormant identifiers for later adoption). The rule: disassembly that restores a marketable object with identity continuity is installation; identity dissolution is a transformation event. Part replacement is accordingly uninstall plus install — two events, with the bill-of-materials instance updated.

04 · The state machineLegitimate status transitions

dppStatus becomes a closed enumeration with defined transitions, each carrying an authority check:

  • active — the normative operating state; entered at issuance (issuer role) or reinstatement (E11, authority role).
  • suspended (transitional "non-conformant pending re-evaluation" included) — entered by E4/E5 re-evaluation or regulator action; exit is active (re-evaluation pass) or invalid.
  • inactive — the subject is not currently placed on the market (e.g., storage, export); reversible.
  • invalid — terminal for the version: authority-checked E11 (regulator or EO per profile), misissuance findings, or adjudicated fraud; the event log remains verifiable.
  • archived — Tier C archival state (EN 18221/OAIS); read-only, retained for the legally required horizon.

Two rules keep the machine honest. Status changes are events (E11), never field writes: the log records who held the authority and under which profile. And profile growth never changes identity: adding a new jurisdiction's profile to an existing product is a registry applicability event with an effective window — including retroactive flags where the law says so — not a new passport.

05 · Time and validityISO 8601, ISO 34000, as-of queries

The time basis is the one the series already cites normatively: ISO 8601-1 and ISO 8601-2, including Amendment 1 (time deviations), with ISO 34000 supplying the event vocabulary. All timestamps are UTC with explicit offset handling; the framework's test suite rejects the defects observed in the corpus (an Annex B example in EN 18223 prints an invalid timestamp using en-dashes in the very clause that teaches the format — validator-enforced, not publication-hoped).

Validity is modelled with two authoritative query modes, because the law needs both:

  • Live view — the current state of the passport, with every element labelled by freshness (staleness is a displayed verdict, never silence).
  • As-of snapshot — the notarized, log-anchored reconstruction of what was legally true at time T: "was this product compliant with profile P when sold in 2028?" As-of answers are reproducible because event order is total in the anchored log and registry versions are pinned per validation.

Between the two sit the three verification readings defined in paper 5 (evidentiary, current-state, cryptographic); verdicts state which reading they answer. Retroactivity of revocation follows the reason taxonomy there: prospective reasons preserve pre-event as-of validity; retroactive reasons (misissuance, fraud) void it ab initio within an explicit window.

Freshness requirements are gated by capability class (paper 1, §04): profiles declare, per data element, the required truth mode (attest-sampled, self-committed, or both with precedence), and the requirement must be satisfiable by the class — an S0 (silent, testimony-only) product cannot satisfy a live-freshness profile.
